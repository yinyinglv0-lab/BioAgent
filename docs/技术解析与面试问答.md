# BioAgent 技术解析与面试问答

> 本文档逐环节讲解 BioAgent 的设计原理、技术与实现,并给出面试高频追问的参考答案。
> 用途:①自己吃透项目 ②面试前复习。代码行号以当前版本为准。

---

## 一、整体架构:一次对话的完整生命周期

BioAgent 的本质是一个 **LLM + 工具调用循环(tool-calling loop)** 的 Agent。

### 1.1 架构分层(自顶向下)

```
接口层    Web UI (FastAPI) / CLI (-q 单问) / Python API
              │ 都调用同一个 BioAgent.chat()
核心层    src/agent.py
              ├─ 系统提示词 SYSTEM_PROMPT(工具清单 + 使用规范 + 文风约束)
              ├─ 多轮工具调用循环(最多 8 轮)
              ├─ 会话历史管理(窗口 = 最近 20 条)
              └─ Provider 抽象:anthropic 原生 tools / openai 兼容 function calling
工具层    src/tools/ 注册表(12 个工具,一处定义 → 两种 API 格式)
              └─ 每个工具 = 一个 Python 函数 + 一个 JSON Schema
数据层    10 个公共生物数据库 REST API(全部免费、无需密钥)
```

### 1.2 一次查询的逐步时序(以 "Analyze TP53..." 为例)

```
第 1 步 用户消息 → chat() 追加到 conversation_history
第 2 步 组装 messages:system prompt + 最近 20 条历史
第 3 步 调用 LLM(带上 tools 参数 = 12 个工具的 JSON Schema)
第 4 步 LLM 返回:
        ├─ 无 tool_calls → 直接返回文本答案(对话结束)
        └─ 有 tool_calls → 解析出 [{name, arguments}]
第 5 步 execute_tool(name, arguments) 本地执行,得到 JSON 结果
第 6 步 结果以 {"error": ...} 或数据的形式追加进 messages,回到第 3 步
第 7 步 最多循环 8 轮;超过则返回 "Agent reached maximum turns"
```

**为什么要有第 6 步的"回填"?** 因为 LLM 每次调用都是无状态的,它只能看到你发给它的全部消息。工具结果必须写回 messages,模型才知道"我查到的 UniProt 结果是什么",才能基于真实数据作答,而不是编造。这一步叫 **tool result feedback**,是整个 Agent 正确性的关键。

### 1.3 关键参数

| 参数 | 值 | 为什么 |
|---|---|---|
| `max_turns` | 8(对话)/ 10(管线) | 防止模型无限循环调工具烧 token;同时兜底"任务无法完成"的情况 |
| `temperature` | 0.3 | 科研问答需要稳定、可复现,不希望发散 |
| `max_tokens` | 4096 | 单轮输出上限 |
| 历史窗口 | 最近 20 条 | 控制上下文长度,防止超长对话撑爆 token 预算 |

## 二、核心设计决策(面试必问,逐个讲清)

### 2.1 为什么不用 LangChain / AutoGen?

**原理对比:**

| | LangChain | BioAgent(原生 API) |
|---|---|---|
| 抽象层次 | AgentExecutor 多层层封装,学习成本高、黑盒多 | 直接调用 Anthropic/OpenAI 的 tools 参数 |
| 代码量 | 同类功能 500+ 行 | 核心 agent.py 仅 ~200 行 |
| 排错难度 | 报错堆栈深,难定位 | 每一轮请求/响应都可见 |
| 可控性 | 受框架版本、API 变更影响 | 完全掌控 schema、历史、错误处理 |

**结论:** 当工具调用模式很简单(LLM 决定调哪个工具 → 执行 → 回填结果)时,框架带来的抽象成本大于收益。原生 API 的工具调用就是为此设计的。面试官追问"什么时候会用 LangChain?"——答案是:需要复杂编排(多 Agent 协作、复杂记忆管理、可观测性生态)时再引入,而不是一开始就上框架。

### 2.2 工具注册表:一处定义,两种格式(provider 无关)

这是项目里最值得讲的设计。核心代码在 `src/tools/__init__.py`:

```python
TOOL_REGISTRY: dict[str, dict] = {}

def register(name, description, input_schema):
    def decorator(func):
        TOOL_REGISTRY[name] = {"name": name, "description": description,
                               "input_schema": input_schema, "func": func}
        return func
    return decorator
```

**设计原理:** 工具的"描述"是给 LLM 看的(schema),工具的"实现"是给自己跑的(func)。两者解耦后,同一份注册信息可以转换成任意 provider 需要的格式:

- Anthropic:`ToolParam(name, description, input_schema)`
- OpenAI 兼容:`{"type": "function", "function": {"name", "description", "parameters"}}`

**好处(逐条都能展开讲):**
1. **换大模型零改动** — 切 Claude ↔ DeepSeek 只改 `.env` 一个变量,12 个工具不用动
2. **加工具只需一处** — 写一个函数 + 一个 schema,import 即注册(模块底部 `from . import xxx` 触发)
3. **工具可独立测试** — 不启动 LLM 也能直接测函数(测试文件就是这么做的)
4. **schema 即文档** — description 写得好不好直接决定模型会不会用这个工具

**JSON Schema 的作用:** 它告诉 LLM:这个工具有哪些参数、哪些必填、什么类型、参数取值范围(enum)。LLM 据此生成结构化的 `arguments`。所以 `required: ["gene"]`、`enum: ["all","title",...]` 这些字段不是装饰,是**约束模型输出的契约**。

### 2.3 优雅降级:错误作为数据,而非异常

```python
try:
    result = execute_tool(name, inputs)
except Exception as e:
    result = {"error": str(e)}
```

**原理:** Agent 语境下,"工具挂了"不是程序故障,而是**一种信息**。如果抛异常让程序崩溃,用户什么也得不到;如果把 `{"error": "API unavailable: ..."}` 回填给 LLM,模型会:
1. 如实告诉用户该数据库暂时不可用
2. 主动换另一个数据库查(系统提示词里教过它工具间的替代关系)
3. 基于已有知识作答并注明数据来源限制

demo 实录里就有实例:ClinVar/cBioPortal 无记录时,模型说明了情况、给出替代来源链接、改用 UniProt + 文献作答。**面试时直接拿这个真实例子讲,说服力极强。**

### 2.4 会话历史与上下文窗口管理

- 完整历史存在 `self.conversation_history`(用户可见的对话)
- 每次调用只取**最近 20 条**拼进请求 → 控制 token 消耗
- Anthropic 分支还会过滤掉"带工具调用的 assistant 消息"(因为 tool_use block 无法简单重发)
- OpenAI 分支用 `"[used tools]"` 占位符保持消息序列完整

**诚实承认局限(面试加分项):** 目前是"截断"而非"摘要"策略,超过 20 条的早期内容会丢失;Anthropic 分支丢弃工具轮次会损失部分上下文。改进方向:用 LLM 做滚动摘要(moving summary),或维护结构化记忆。

### 2.5 系统提示词设计(研究 agent 的关键)

`SYSTEM_PROMPT` 分三块,各有目的:
1. **工具清单与调用指南** — 每个工具一句话说明 + "查基因时用 UniProt/Ensembl/KEGG 三库交叉"等路由规则
2. **回答规范** — "引用 PubMed 支持论断"、"给生物学家讲人话"、"基因符号大写"
3. **文风硬约束** — 禁 emoji、学术口吻、标准 Markdown、层级化组织

**原理:** 工具型 agent 的提示词是"路由表 + 风格指南"。第 2、3 块决定输出质量的下限——没有这些,模型会输出营销腔、乱用表情、不引用来源。

## 三、每个工具的实现原理(数据层逐个拆解)

### 3.1 NCBI E-utilities:esearch → esummary/efetch 两步法

PubMed、GEO、ClinVar、dbSNP 四个工具共用这套模式:

```
第 1 步 esearch.fcgi?db=pubmed&term=...&retmode=json
        → 返回匹配的 ID 列表 + 真实总数 count
第 2 步 esummary.fcgi 或 efetch.fcgi?id=1,2,3...
        → 按 ID 批量取详情
```

**要点:**
- **总数用 `esearch.count` 而不是返回条数** — 这是修过的一个真实 bug(见 §5.4)
- **字段限定符**:`BRCA1[Title]`、`Smith J[Author]`、`...[MeSH Terms]` 是 PubMed 的查询语法,工具层做了映射,让 LLM 只需选 `search_field="title"`
- **限速**:E-utilities 无密钥 3 req/s、有密钥 10 req/s;本项目没有实现节流,是 roadmap 项
- ClinVar 用 `clinsig pathogenic[filter]` 只捞致病性变异;dbSNP 靠 `rs` 前缀区分 rsID 和基因查询

### 3.2 UniProt REST:查询语法 + 注释解析

```python
query = f"(gene:{gene}) AND organism_id:9606"   # 限定人类
```

- 用 `comments`(commentType=FUNCTION/DISEASE)拿功能和疾病关联
- 用 `features`(type=DOMAIN)拿结构域及起止坐标
- 限定 `size=3`,只取前 3 个蛋白(避免同名基因多个蛋白刷屏)

### 3.3 Ensembl REST:两段式解析

```
符号 → ID:   GET /xrefs/symbol/homo_sapiens/{gene}   (拿 ENSG ID)
ID → 详情:   GET /lookup/id/{ENSG}?expand=1          (染色体/坐标/链/biotype)
```

如果输入已经是 ENSG 开头,直接跳过第一步。`expand=1` 让返回带上额外注释。

### 3.4 KEGG REST:find → 最佳匹配 → get

KEGG 没有 JSON API(纯文本),三步走:
1. `find/genes/{keyword}` 模糊搜索,过滤 `hsa:` 前缀(只要人类)
2. **最佳匹配启发式**:模糊搜索结果里第一个符号精确等于关键词的那条优先;否则取第一条。解决"BRCA1 能搜出一堆 BRCA1xxx"的同名问题
3. `get/{hsa_id}` 拿条目全文,按 `PATHWAY` 行缩进规则解析通路列表(KEGG 文本格式:续行以空格开头)

**这个"同名基因精确匹配"是一个很自然的面试故事**:直接用第一条结果会答错基因。

### 3.5 cBioPortal(TCGA):三步级联

```
studies?pageSize=100            → 按 cancerTypeId/name 过滤出研究
studies/{id}/molecular-profiles → 找 MUTATION_EXTENDED 突变谱
molecular-profiles/{id}/mutations?geneList=TP53&projection=SUMMARY
                                → 基因在全部样本中的突变列表
```

原理:cBioPortal 的数据模型是"研究(study)→ 分子谱(profile)→ 数据"。必须按层级一级级拿 ID。

### 3.6 STRING:TSV 接口与列映射(修过严重 bug,见 §5.5)

- 多基因用 `%0d`(URL 编码的换行)连接
- `tsv/network` 13 列:`stringId_A/B, preferredName_A/B, ncbiTaxonId, score, nscore...tscore` — 前两列是内部 ID,**基因名在第 3、4 列**;score 是综合得分,后 7 列是各证据通道得分(neighborhood/fusion/cooccurrence/coexpression/experiments/database/textmining)
- `tsv/enrichment` 10 列:`category, term, ..., inputGenes, preferredNames, p_value, fdr, description` — 描述文本在**最后一列**

### 3.7 g:Profiler:POST JSON 富集分析

```json
POST https://biit.cs.ut.ee/gprofiler/api/gost/profile/
{"organism": "hsapiens", "query": ["TP53","EGFR","KRAS"],
 "sources": ["GO:BP","GO:MF","GO:CC","KEGG","REAC"], "user_threshold": 0.05}
```

- 免费无密钥,超几何检验 + 多重检验校正,返回 p_value / fdr / intersection_size
- 结果按 p 值排序,**每个来源保留 Top5**(避免 LLM 上下文被几百条术语淹没)
- 注意:`intersections` 字段返回的是证据代码(GO 的 IDA/ISS/IEA),不是基因名——API v2 的行为,字段已命名为 `evidence_codes`

### 3.8 read_paper:PDF 解析与正则分节

- 首选 PyMuPDF(fitz),ImportError 时降级到 pypdf —— **双引擎降级**
- 正则提取:标题(首行)、Abstract 段落(直到 Introduction/Background 为止)
- 基因符号提取:`\b[A-Z]{2,}[0-9]*[A-Z]*\b` —— 纯启发式,会误报 DNA/RNA 等词,**诚实标注为 potential_gene_symbols**

## 五、工程踩坑记录(面试讲故事的弹药库)

每个坑都是"发现问题 → 定位 → 修复"的完整故事,面试讲 2-3 个就很出彩。

### 5.1 Windows GBK 编码乱码
- **现象**:CLI 重定向输出到文件后,en-dash(–)等字符变成乱码
- **定位**:中文 Windows 的 stdout 默认 GBK(cp936),DeepSeek 返回 UTF-8 文本,Python 按 locale 编码写出 → 文件里是 GBK 字节,GitHub 上显示乱码
- **修复**:`cli.py` 开头 `sys.stdout.reconfigure(encoding="utf-8")`

### 5.2 SSL 证书链验证失败
- **现象**:UniProt/KEGG 正常,g:Profiler 报 `CERTIFICATE_VERIFY_FAILED`
- **定位**:Windows 默认 CA 列表不完整,部分站点(Let's Encrypt 链)验证失败
- **修复**:统一 `ssl.create_default_context(cafile=certifi.where())`,且 certifi 缺失时静默降级回系统默认。所有 HTTP 调用共用此 context

### 5.3 STRING TSV 列错位(最严重的 bug)
- **现象**:`query_string_network` 在有数据时抛异常;`query_string_enrichment` 的 fdr 恒为 1.0
- **定位**:按记忆中的列号解析,与 STRING 实际返回不符——基因名读成了内部 ID(`9606.ENSP...`),把 `preferredName` 当分数解析(int("TP53") 抛 ValueError),fdr 列读成了基因列表字符串(float 失败被 except 吞掉,静默赋 1.0)
- **修复**:用真实 API 响应核对 13/10 列格式,重写映射;分数解析用安全转换 `_to_float`
- **教训**:**第三方的列格式必须用真实响应验证,不能凭印象**;except 吞异常要留日志,不能静默给默认值

### 5.4 PubMed 总数失真
- **现象**:报告"共 10 篇"其实有几千篇
- **定位**:把 `retmax`(本次返回条数)当总数
- **修复**:改用 `esearch.count`(PubMed 真实命中总数),并让 `max_results` 不影响 count

### 5.5 富集分析假数据
- **现象**:`run_enrichment` 返回的是 7 个基因的硬编码 GO 注释
- **修复**:重写为调用真实的 g:Profiler REST API,支持人/鼠/大鼠,按来源分组取 Top5
- **面试视角**:主动把 demo 数据替换为真实 API,是"知道什么不能写进简历"的体现

### 5.6 测试引用不存在的函数
- **现象**:`test_tool_registry` ImportError(`get_all_tools` 不存在)
- **修复**:补上 `get_all_tools()`(本来就该是公共 API),并把期望工具数从 10 更新为 12

## 六、已知局限与改进方向(诚实清单,面试主动说)

1. **E-utilities 无限速**:无密钥 3 req/s,连续多工具调用可能被拒 → 待加节流/重试
2. **历史窗口是截断不是摘要**:>20 条早期上下文丢失 → 可加滚动摘要
3. **无流式输出**:Web UI 要等完整回答 → SSE/streaming
4. **PDF 分节是朴素正则**:双栏论文、无 Abstract 的论文效果差 → 布局分析模型
5. **基因符号正则误报**:DNA/RNA 等词会被误提 → 用官方基因名表过滤
6. **read_paper 路径任意读**:agent 可读本机任意路径(本机工具的正常行为,但需在文档中声明安全边界)
7. **无 RAG 私有知识库**:只查公共 API → 可加 ChromaDB 本地文献库

## 七、面试高频追问 12 问(参考答案要点)

1. **Q:为什么不直接用 LangChain?**
   A:见 §2.1。核心论点:工具调用是简单模式,原生 API 200 行搞定;框架价值在复杂编排,需要时再引入。

2. **Q:一次对话从用户提问到答案,数据流是怎样的?**
   A:见 §1.2 的 7 步时序,重点是"tool result 必须回填,否则模型是瞎编"。

3. **Q:怎么做到 Claude 和 DeepSeek 无缝切换?**
   A:注册表单一来源,两个转换函数输出各自的 schema 格式;Provider 分支只在消息组装上不同。改 `.env` 即可。

4. **Q:模型会不会乱调工具、传错参数?**
   A:会。三重防护:①schema 里 required/enum/type 约束;②execute_tool 异常兜底成 {"error"};③历史回填让模型看到错误后自我纠正。另外 temperature=0.3 降低随机性。

5. **Q:某数据库 API 挂了怎么办?**
   A:优雅降级(§2.3):错误作为数据回填,模型说明限制、换库、给替代链接。demo 实录有真实案例。

6. **Q:上下文越来越长怎么控制?**
   A:窗口截断 20 条 + 工具结果本身是压缩后的结构化 JSON(不是原始网页)。改进方向是摘要式记忆。

7. **Q:PubMed 搜索为什么要自己做字段限定符映射?**
   A:让 LLM 选枚举值比让它拼 `[Title]` 语法更可靠——把语法复杂度收进代码,模型的决策面变小,出错率下降。

8. **Q:KEGG 为什么不能直接取第一条搜索结果?**
   A:同名/相似符号问题(§3.4),BRCA1 会命中 BRCA1xxx,必须有精确符号匹配的启发式。

9. **Q:STRING 返回的列你怎么知道含义?**
   A:官方文档 + 真实响应核对(§5.3 的教训)。写工具 = 写解析器,列格式必须实测。

10. **Q:为什么工具都用 urllib 而不是 requests/httpx?**
    A:12 个工具只需要 GET/POST + JSON,urllib 零依赖、行为可控;requirements 里的 httpx 留给未来更复杂的场景。**追问**:那怎么保证超时?—— 每个请求 timeout=10~20s,失败即返回 error,不阻塞 agent 循环。

11. **Q:如果要把这个 agent 接入 RAG 私有文献库,怎么设计?**
    A:新增 `search_local_kb` 工具:文档切分 → BGE 向量化 → ChromaDB 检索 → 混合 BM25;注册表机制下就是加一个工具的事,架构零改动。(你有成本分析系统的实战经验,可以直接讲)

12. **Q:这个项目最难的一个 bug 是什么?**
    A:讲 §5.3 STRING 列错位:现象(有数据就崩、fdr 恒 1.0)→ 定位(except 吞异常让 bug 静默)→ 修复(真实响应核对重写映射)→ 沉淀(第三方格式必须实测;异常处理不能吞掉关键信息)。

## 八、一分钟项目介绍(面试开场模板)

> BioAgent 是我独立开发的生信科研 AI 助手:用户用自然语言提问,Agent 自动决策并调用 12 个工具,查询 UniProt、KEGG、TCGA、STRING、PubMed 等 10 个公共生物数据库,最后综合成带文献引用的学术综述式回答。技术上,核心是一个 200 行的原生工具调用循环,不依赖 LangChain;工具注册表用"一份 schema 转两种格式"的设计,做到 Claude 和 DeepSeek 等五家模型零改动切换;所有工具失败都走优雅降级,错误作为数据回传给模型。项目有 Web UI、CLI、Python API 三种入口,Docker 一键部署,7 个自动化测试含真实 API 冒烟测试,已在 GitHub 开源。
